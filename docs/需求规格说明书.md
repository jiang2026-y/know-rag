## 2. 产品背景与目标

汽车企业的车型资料、购车政策、使用手册、售后服务规范、技术资料和业务数据分散在不同系统中。普通消费者需要快速了解品牌、车型和购车服务；已购车车主还需要查询与本人车辆有关的保养、质保和服务信息；内部员工则需要高效获取制度、产品、销售、售后及技术支持知识。

本系统为三类用户提供统一的自然语言问答入口。系统先识别提问者身份和问题意图，再按权限检索企业知识库、关系型数据库和图数据库，最后以带引用的流式回答返回结果。闲聊或非汽车领域问题不访问企业内部数据，直接由通用对话模型处理。

目标如下：

- 为普通顾客提供准确、一致的公开汽车产品与服务咨询体验。
- 为已购车车主提供经身份校验后的车辆专属服务问答，保护个人与车辆数据。
- 为内部员工提供受岗位权限约束的企业知识和业务辅助问答。
- 将文档接入、检索、回答、反馈和运营分析沉淀为可扩展、可维护的长期能力。

## 3. 用户角色与访问边界

本系统面向问答服务的主要用户角色仅包含以下三类。后台知识维护、内容运营和系统配置属于管理能力，不作为面向问答的主要用户角色。

| 角色 | 身份定义 | 可咨询内容 | 不可访问内容 |
| --- | --- | --- | --- |
| 普通顾客 | 未绑定车辆的外部消费者，包括意向购车用户和一般访客。可匿名或完成基础账号认证。 | 公开车型信息、配置说明、购车流程、公开价格或活动规则、门店与售后服务说明、公开 FAQ。 | 其他车主信息、个人订单、车辆专属记录、内部资料、未公开政策和经营数据。 |
| 已购车车主 | 已完成账号与车辆或订单绑定验证的外部顾客。 | 普通顾客可访问内容，以及本人车辆的保养建议、质保状态、已授权的订单/服务进度、召回或活动通知、车主服务流程。 | 其他车主信息、超出授权范围的维修明细、内部资料、未公开经营数据。 |
| 企业员工 | 使用现有 MySQL 账号密码认证的内部人员；P0 实际可访问范围仅由在职状态和固定岗位值 `staff`、`leader` 决定。 | 公开知识，以及按员工类别授权的制度流程、车型资料、销售服务规范、技术手册、培训资料、业务指标和受控图谱关系。 | 不属于当前员工类别的内部文件、其他员工或顾客的非必要个人信息。 |

### 3.1 角色判定原则

1. 顾客账号未完成车辆或订单绑定时，按普通顾客处理。
2. 已购车车主资格必须由可信业务系统或已确认的绑定流程判定，不能由用户在对话中自行声明。
3. 员工身份必须来自受控 MySQL 员工账号体系；P0 仅使用在职状态与固定岗位值 `staff`、`leader` 构造权限属性，`dept_id` 暂不参与知识授权。
4. 身份缺失、校验失败或权限服务不可用时，系统只能返回公开知识；不得返回车辆专属、顾客个人或内部信息。

### 3.2 后台管理能力说明

知识库管理员、运营人员和系统管理员是后台管理权限，不是新的问答人群。后台能力包括文档上传、知识审核、处理任务重试、知识可见范围配置、日志分析、反馈处理、模型与数据源配置；其权限模型应与上述三类问答用户分离。

## 4. 范围与业务场景

### 4.1 本期范围

1. 将 PDF、Word、CSV、Excel 等企业资料接入 MinerU，转换为 Markdown 后完成智能切片、向量化和 Elasticsearch 索引。
2. P0 为 Next.js + TypeScript Web 前端提供统一问答服务；钉钉机器人等渠道放入 P1。
3. 依据普通顾客、已购车车主、企业员工三类身份识别意图、控制检索范围与回答内容。
4. 支持知识库、关系型数据库、图数据库的受控路由、并行检索和结果重排。
5. 支持父子分段回溯、兄弟分段补全、引用生成和 LLM 流式回答。
6. 持久化查询、路由、召回、回答和反馈记录，支撑运营优化与审计。

### 4.2 P0 固定边界与明确不做

P0 的目标是在 **Web 渠道** 跑通普通顾客、已购车车主和企业员工三类用户的完整、按身份授权的汽车问答闭环：认证或身份解析、受控检索、带引用的 SSE 回答、任务状态查询、错误降级、审计和反馈。

| 项目 | P0 固定范围 | P0 不做或后移 |
| --- | --- | --- |
| 渠道 | Next.js App Router + TypeScript Web 前端及 FastAPI Web API。 | 钉钉机器人及其他渠道适配放 P1。 |
| 用户角色 | 普通顾客、已购车车主、企业员工均完成真实权限问答与越权测试。 | 以“模拟角色”替代可信身份、车辆或岗位授权。 |
| 知识与数据 | 受审核企业文档、受控 MySQL 只读业务数据、受控 Neo4j 图数据。 | 任意网页抓取、任意 SQL/Cypher、未经审核的外部内容。 |
| 问答能力 | 意图、改写、数据源路由、混合检索、重排、引用和 SSE 回答。 | 多 Agent 自主协作、长期记忆、自动向外部系统写入或发布。 |
| 异步能力 | Celery + Redis + Relier 的文档、向量化、索引、审计与可恢复任务。 | 仅依赖 Web 进程内后台任务作为生产可靠性机制。 |
| 代码沙箱 | Python 代码分析和测试；仅处理经用户明确授权的白名单文件。 | 面向问答用户开放通用代码执行、Shell、任意依赖安装或网络访问。 |

P0 不因角色“完整支持”而放宽任何数据边界：车主绑定来源、员工权限范围及其变更撤销规则尚未确认时，该角色的专属数据功能不得以猜测、默认放行或静态示例替代，必须阻断上线或仅降级为公开知识回答。

### 4.3 典型场景

| 用户 | 示例问题 | 预期处理 |
| --- | --- | --- |
| 普通顾客 | “这款 SUV 的续航和安全配置如何？” | 从公开车型资料检索，回答并引用车型手册或官网资料。 |
| 普通顾客 | “附近有哪些门店？” | 路由至公开门店知识或受控业务数据，返回可公开的门店信息。 |
| 已购车车主 | “我的车什么时候该保养？” | 验证车辆绑定与授权后，结合车辆档案、保养规则和知识库回答。 |
| 已购车车主 | “我的质保还有多久？” | 仅查询当前车主获授权车辆的质保数据，不能暴露其他车辆信息。 |
| 企业员工 | “某车型的交付前检查流程是什么？” | 基于员工岗位权限检索内部流程和技术资料，并附内部来源引用。 |
| 企业员工 | “某零部件与哪些故障码有关联？” | 在权限允许时路由图数据库和技术知识库，合并关系与文档证据。 |
| 任意用户 | “今天天气怎么样？” | 判定为非汽车领域问题，进入通用对话，不检索企业数据。 |

## 5. 端到端业务流程

### 5.1 知识入库流程

~~~text
企业资料上传
  → 文件校验与类型检测
  → MinerU 异步转换为 Markdown
  → 标题 + 父子 + 分隔符 + 字数智能切片
  → 雪花算法生成分段 ID 与关系元数据
  → 向量化
  → Elasticsearch 写入向量、全文与 metadata 索引
  → 文档状态更新并可供检索
~~~

### 5.2 智能问答流程

~~~text
用户输入（Web / 钉钉等）
  → 身份识别：普通顾客 / 已购车车主 / 企业员工
  → 意图识别
       ├─ 不相关、闲聊、问候 → 通用大模型流式回答
       └─ 汽车领域相关
            → 查询改写（简洁化、抽象化、术语标准化、纠错）
            → 数据源路由
            → 并行检索（知识库 / 关系库 / 图数据库）
            → 父块回溯、兄弟块补全、再次权限校验
            → 多源重排序与上下文聚合
            → 生成引用 + 领域 Prompt
            → SSE 发送查询改写进度与查询结果
            → LLM 流式生成回答事件
            → 多渠道展示，并异步记录日志与反馈
~~~

## 6. 功能需求

### 6.1 身份、会话与权限

#### FR-AUTH-001 统一身份上下文

每次问答请求必须形成统一身份上下文，至少包括用户 ID、用户角色、渠道、会话 ID、认证状态和权限范围。已购车车主额外携带经过验证的可访问车辆或订单范围；员工在 P0 额外携带在职状态和 `job=staff`、`job=leader` 构造的知识权限范围。

#### FR-AUTH-002 最小权限检索

系统必须在数据源查询前附加角色和权限过滤，并在补全父块、兄弟块及生成引用时再次校验。以下规则必须成立：

- 普通顾客仅检索公开知识与公开业务信息。
- 已购车车主仅检索公开信息和本人被授权车辆、订单、服务记录。
- 员工仅检索公开信息及与其岗位权限匹配的内部知识和业务数据。

#### FR-AUTH-003 认证方式与权威身份映射

企业员工使用现有 MySQL 账号密码认证；当前以 `staff_info.emp_id` 作为稳定员工标识，服务端仅在账号为在职状态且密码校验通过后创建 Redis 服务端 Session。新密码统一保存为 Argon2id（19456 KiB、2 次、1 并行度）；历史 PBKDF2-HMAC-SHA256 仅在成功登录时兼容并自动升级。顾客通过认证接口修改密码时，后端先撤销该顾客全部 Redis Session，再写入新摘要，确保旧登录态立即失效。车主继续使用 Redis 服务端 Session 与 HttpOnly Cookie；P0 仅以 `my_car.user_id` 与 `user_info.id` 的绑定推导当前车主车辆范围，`car_order.user_id` 不单独授予车辆访问。

HR 创建员工主数据后，调用 `POST /internal/v1/hr/staff/{emp_id}/initial-password` 设置初始密码。该接口只接受内部网络中配置了 `X-Internal-Service-Token` 的服务调用，必须携带 `Idempotency-Key`；仅对已存在、`status=ON_JOB` 且密码为 `NULL` 或空字符串的员工生成 Argon2id 摘要。接口不创建员工、不返回或审计密码及密码摘要；成功操作记录服务名、目标工号、结果和 `trace_id` 六个月，并在写入前撤销目标员工全部 Redis Session。

系统必须采用“**MySQL 权威授权数据 + Neo4j 关系图谱**”方案：MySQL 中员工账号的 `status` 与固定岗位值 `staff`、`leader` 是 P0 员工知识授权依据；`dept_id` 暂不参与知识授权。Neo4j 仅承载员工、组织、知识域及车主关联等受控关系查询。图谱同步延迟、关系不完整或图查询失败时必须按最小权限降级，不能将图遍历结果直接视为授权结论。

#### FR-AUTH-004 权限版本失效

每次私有数据访问均必须校验当前服务端 Session。车辆解绑、过户、员工状态或部门变更后，后端必须立即清除受影响主体的全部 Redis Session；后续请求不得复用旧会话、旧缓存或旧检索结果中的权限范围，必须重新登录并按最新权限构造 `AccessContext`。撤销操作失败时应拒绝该主体的私有访问并告警；失效或校验失败时仅返回公开知识。

#### FR-CHAT-001 多渠道统一会话

系统应支持 Web、钉钉机器人及后续渠道接入，并将不同渠道消息转换为统一会话模型。会话中保存用户消息、助手消息、用户角色、身份快照、引用、意图、路由、反馈和必要运行元数据。会话标题可异步生成，不得阻塞回答流。

#### FR-CHAT-002 隐私与会话隔离

车主专属会话与员工内部会话不得向无权限身份共享、导出或复用。用户角色或权限发生变化后，后续提问必须使用最新权限重新检索，不得仅复用旧会话上下文。

### 6.2 文档接入、解析与治理

#### FR-DOC-001 文档上传与分类

后台管理端应支持上传 PDF、DOC、DOCX、CSV、XLS、XLSX 文件。每份文档至少记录知识域、适用用户角色、可见范围、车型或产品范围、区域、版本、生效状态、来源、上传人和更新时间。

P0 知识文档仅可分类为 `VISITOR`、`STAFF`、`LEADER`；标签必须成为 Elasticsearch `metadata.accessibleBy` 的精确过滤条件。普通员工检索范围为 `VISITOR`、`STAFF`，领导检索范围为 `VISITOR`、`STAFF`、`LEADER`；车型、区域、部门和车主专属标签后续再启用。

#### FR-DOC-002 MinerU 转换与任务状态

系统应对上传文件进行类型检测并异步提交 MinerU，转换为 Markdown；原始文件、Markdown、解析图片和任务结果应关联存储。处理任务至少支持 queued、processing、converted、chunked、vector_stored、failed、cancelled 状态，失败原因可查询且支持受控重试。

#### FR-DOC-003 文档生命周期

系统应支持文档版本、启用、停用、归档和删除。资料失效、下架或权限变更后，系统应从后续检索结果中排除相应内容，并保留审计记录。

### 6.3 智能切片、向量化与检索索引

#### FR-CHUNK-001 智能切片

Markdown 文档应按标题和标题层级构建段落上下文，并采用标题、父子分段、自然分隔符和字数限制的组合策略：

- 保留当前段落及父级标题路径。
- 超长内容保存完整父块，并生成带重叠的可检索子块。
- 优先在段落、列表、表格或句子边界切分，减少 Markdown 结构破坏。
- 切片大小、重叠长度和策略版本应可配置并可追踪。

已落地的切片策略与参数（`POST /api/documents/upload` 的可选表单字段，缺省等价于既有行为）：

| 策略 | 行为 | 关键参数 |
| --- | --- | --- |
| `TITLE`（默认） | 按 1..`title_level` 级标题切分章节，超长章节保留完整父块并生成重叠子块 | `title_level`（1-6，默认 6）、`chunk_size`、`overlap` |
| `SMART` | 与 `TITLE` 相同的切分方式，重叠固定为 `chunk_size × 10%` | `chunk_size`（默认 1000） |
| `LENGTH` | 按长度与重叠平铺切分，不产生父子分片 | `chunk_size`、`overlap` |
| `SEPARATOR` | 先按字面分隔符切分，超长片段再生成父子分片 | `separator`（必填）、`chunk_size`、`overlap` |
| `REGEX` | 先按正则切分，超长片段再生成父子分片 | `regex`（必填且必须可编译）、`chunk_size`、`overlap` |

参数约束：`chunk_size` 取 1-8000（默认 1000）；`overlap` 取 0 到 `chunk_size-1`，未显式指定时按
`min(100, chunk_size-1)` 收敛；`title_level` 取 1-6；`separator` 与 `regex` 互斥且均不超过 200 字符。
任一违规返回 422，不写入文档版本记录，也不上传源文件；切片参数按文档版本持久化，后台任务按记录取值执行。

#### FR-CHUNK-002 分段元数据与雪花 ID

每个分段必须使用雪花算法生成全局唯一 ID，保存文档 ID、知识域、标题路径、父分段 ID、同级顺序、来源链接、车型范围、角色可见范围、权限标签、切片策略版本和向量状态。

#### FR-INDEX-001 向量化与 ES 索引

系统应对可检索子块生成向量，并在 Elasticsearch 建立向量、全文和 metadata 检索能力。索引至少支持：

- 向量相似度检索；
- 中文全文检索；
- 角色、可见范围、车型、区域、文档状态、标签等 metadata 过滤；
- 文档级删除、停用、重建和批量重建；
- 对 Embedding Provider、模型、维度、版本和生成结果的追踪。

P0 固定使用 DashScope `text-embedding-v4`（1536 维）。该维度、模型和版本必须进入 Elasticsearch 索引与分段元数据；任何变更均须新建索引或执行受控全量重嵌入，禁止将不同维度向量写入同一索引。

### 6.4 意图识别与查询改写

#### FR-INTENT-001 结构化意图识别

系统应结合服务端可信用户角色和问题内容调用 DashScope `qwen3.5-flash`，输出经过 Pydantic JSON Schema 校验的结构化结果。P0 固定字段如下：

~~~json
{
  "related": true,
  "intent": "车辆使用与技术指导",
  "entities": {
    "car_model": null,
    "order_id": null,
    "dealer": null,
    "fault_description": null,
    "appointment_time": null,
    "part_name": null,
    "function_name": "自适应巡航",
    "warning_light": null
  },
  "reasoning": "用户询问车辆功能操作方法。"
}
~~~

`intent` 只能是“售前咨询与购买、售后维修与保养、车辆使用与技术指导、投诉与维权、汽车营销政策、闲聊与通用问答、其他”之一。`entities` 固定包含车型、订单号、门店、故障描述、预约时间、零部件、功能和警告灯；未提及的字段为 `null`。当 `related=false` 时，`intent` 必须为“闲聊与通用问答”，八项实体必须全部为 `null`。`reasoning` 仅保存不超过 200 字的可解释判断摘要，不得要求、存储或向用户展示模型完整思维链。

#### FR-INTENT-002 不相关问题处理

当问题为闲聊、问候、非汽车领域问题或明确不使用企业数据的请求时，系统应转至通用对话服务流式回答，不访问企业知识库、车主数据、员工数据或图数据库。

#### FR-INTENT-003 查询改写与异步记录

查询改写在意图识别之后执行。汽车相关问题使用 `qwen3.5-flash` 按简洁化、抽象概念化和错别字纠正三种策略生成单一检索查询；原始问题继续保存在 `chat_message.content`，改写结果、状态和模型版本写入同一消息的 `metadata.queryRewrite`。改写失败时使用原查询，不阻塞回答；非汽车问题不调用改写模型，也不访问企业内部数据。

### 6.5 数据源路由与并行检索

#### FR-ROUTE-001 路由决策

系统应根据用户角色、身份验证结果、意图、问题类型和实体生成一个或多个路由决策：

| 路由值 | 数据源 | 角色适用规则 |
| --- | --- | --- |
| knowledge_base | Elasticsearch 企业知识库 | 三类用户均可使用，但按公开、车主、员工及岗位范围过滤。 |
| relational_db | 关系型业务数据库 | 仅已认证车主查询本人授权数据，或有权限员工查询受控业务数据。 |
| graph_db | Neo4j 图数据库 | P0 仅查询公开的品牌、车型、版本、能源类型、配件及兼容关系；不存储或查询顾客、员工、订单和车辆绑定数据。 |
| general_chat | 通用大模型 | 三类用户的非领域或闲聊问题均可使用，禁止读取企业私有数据。 |

#### FR-ROUTE-002 并行检索与降级

命中多个数据源时，系统应并行检索，并对每个数据源设置超时、限流、重试和降级策略。个人车辆查询默认使用 `relational_db + knowledge_base`，纯技术问题默认使用 `knowledge_base`，车型关系问题默认使用 `graph_db + knowledge_base`。各路结果先按统一 RRF（`k=60`）融合，再进入统一重排；单一数据源失败不得丢弃其他成功结果。若车主专属数据不可用，应明确提示“暂无法查询个人车辆信息”，不得以猜测结果替代。

#### FR-RETRIEVE-001 知识库混合检索

知识库应支持 Elasticsearch 向量检索、全文检索、metadata 过滤与混合召回。原始召回结果至少返回分段文本、命中方式、分数、文档信息、车型/角色标签、权限结果和检索耗时。

已落地的结构化源回落：当本次路由包含 `relational_db` 或 `graph_db`，但所有结构化源均无证据或适配器故障，
且路由未包含 `knowledge_base` 时，编排层补充一次知识库检索（仍按当前主体授权范围过滤），
证据的 `retrieval_methods` 标记 `fallback_from:<strategy>`，并在该轮用户消息的 `retrieval` 审计中写入
`fallbacks: [{from, reason}]`，`reason` 取 `empty_result` 或 `retriever_error`。
路由置信度低于 0.5 的空路由仍然不检索任何数据源，不做无条件兜底。

#### FR-RETRIEVE-002 父子回溯与兄弟补全

当检索命中子块时，系统应：

1. 根据子块 ID 找回完整父块；
2. 按同级顺序补充配置窗口内相邻兄弟块；
3. 在补全后按文档、父块和内容去重，并受上下文 Token 预算限制；
4. 对补全内容再次执行用户角色与权限校验。

已落地的父块正文三级缓存：请求内字典（L1）→ Redis（L2，键 `llmcopy:cache:segment:{chunk_id}`，
TTL 由 `SEGMENT_CACHE_TTL_SECONDS` 控制、默认 30 秒）→ MySQL（L3）。缓存只保存正文，
不保存权限结论；命中缓存后仍必须通过 MySQL 二次授权校验，未授权命中一律丢弃。重新切片、
重新向量化或文档生命周期变更为非 `ENABLED` 时按文档批量失效；Redis 不可用或
`SEGMENT_CACHE_ENABLED=false` 时退化为回源 MySQL。

#### FR-RETRIEVE-003 受控关系库查询

关系型数据库查询必须通过受控 JDBC 或等效数据访问层执行，只允许访问预登记的只读数据源、视图或语义层。LLM 生成的查询必须经过只读性、表列白名单、用户数据范围、行数和超时校验；不得执行任意 SQL。

#### FR-RETRIEVE-004 受控图数据库查询

Neo4j 查询必须通过受控适配器执行，限制图空间、标签、关系类型、返回量与执行时间；禁止由 Agent 或模型拼接 Cypher。图数据库结果应转换为统一召回模型，供重排和引用使用。

### 6.6 重排、引用与回答生成

#### FR-RERANK-001 多源重排序

系统应使用 DashScope `qwen3-rerank` 对统一 RRF 融合后的知识库、关系库和图数据库候选进行归一化、相关性评分和重排序，保留最相关的前 N 个上下文。个人车辆结构化事实优先于知识库通用说明；每条结果需保留原始数据源、原始分数、RRF 分数、重排分数和淘汰原因，用于质量评估。

#### FR-ANSWER-001 上下文聚合与引用

系统应在 Token 预算内合并重排后的内容，生成来源引用。公开顾客回答仅展示公开链接和公开资料；车主回答中的个人数据引用不得泄露内部字段或其他车主信息；员工回答中的内部引用需受当前岗位权限和链接访问控制保护。

每条引用至少包含来源名称、章节或字段说明、受控链接、分段或记录 ID 和引用序号。

#### FR-ANSWER-002 角色化领域 Prompt

系统应使用 DashScope `qwen3.7-plus` 和版本化领域 Prompt 生成回答。Prompt 至少包含用户问题、改写问题、用户角色、已验证权限范围、检索资料、引用规则、回答格式和不确定性约束。

- 面向普通顾客：语言应清晰、友好，不承诺未公开价格、交付日期或权益。
- 面向已购车车主：说明车辆专属信息的查询范围，敏感操作应引导至官方渠道。
- 面向企业员工：保留专业术语和内部来源，但不得超越岗位权限输出。

#### FR-ANSWER-004 多轮会话记忆

回答生成应携带同一会话最近若干条已成功持久化的消息（默认 10 条，由 `CHAT_HISTORY_MAX_MESSAGES`
控制），按 `CHAT_HISTORY_MAX_CHARACTERS`（默认 4000 字符）从最近往前裁剪后拼入提示词，位置在
「已授权知识证据」之前。历史消息只用于生成，不进入引用事件与引用持久化，也不参与权限判定；
读取失败只记录告警并降级为无历史，不得阻断回答。未成功完成的回答（模型失败、取消或空回答）不进入历史。

#### FR-ANSWER-003 可信与安全回答

回答必须以检索上下文为依据并与引用一一对应。证据不足、来源冲突、权限不足或数据源故障时，应明确说明限制，不得编造车型配置、车主记录、政策、来源或内部数据。

### 6.7 Agent 运行时与沙箱

#### FR-AGENT-001 独立 Agent 运行时

Agent 必须作为独立部署的运行时，与业务后端、前端分别隔离。Agent 负责意图识别、查询改写、工具选择、受控检索编排、重排、上下文聚合、Prompt 构建和回答事件组织；业务后端是身份、权限、业务数据和知识数据的唯一可信边界。

- Agent 与业务后端采用同步 HTTP/JSON 调用；业务后端向 Agent 提供版本化的内部工具契约。
- Agent 不得直接连接 MySQL、Elasticsearch、Redis、MinIO、图数据库或业务数据库，也不得持有这些服务的直连凭证。
- 每次工具调用必须携带由业务后端签发或转发的可信身份上下文、权限范围、请求标识和 trace_id；Agent 不得自行扩大权限范围。
- 业务后端必须在每次工具调用中重新执行权限校验、参数校验、脱敏和审计，不得只依赖 Agent Prompt。

#### FR-AGENT-002 预定义工具与沙箱降级

Agent 应首先使用预定义、受控的业务工具解决问题。仅在无匹配预定义工具且用户明确要求“分析代码”时，才允许调用代码分析沙箱；预定义工具调用失败时，仅可对本地代码分析、文件解析或测试验证等本地计算任务降级到沙箱。

- 鉴权失败、权限拒绝、数据库或外部服务故障、模型调用故障不得通过沙箱绕过或重试。
- 沙箱默认只读；仅在用户明确要求修改代码时，才可在一次性临时工作区生成补丁，补丁须经过验证并由主服务显式应用。
- 沙箱仅可访问由受控调度器复制到一次性临时工作区的白名单文件；禁止直接挂载项目根目录，禁止访问宿主机、生产数据、密钥、容器管理接口和未授权网络。
- 当前沙箱仅允许分析和测试 Python 代码；不得在沙箱中提供 Shell、原生 SQL、其他语言运行时或通用代码执行能力。

### 6.8 流式事件、反馈与运营

#### FR-SSE-001 SSE 流式输出

系统应通过 SSE 输出六类统一事件：`progress`、`query_rewrite`、`answer_delta`、`citation`、`error`、`done`。

`progress` 在查询改写开始时发送，负载包含 `stage=QUERY_REWRITE` 和“正在优化您的问题”；`query_rewrite` 返回原查询、改写查询和改写状态。增强查询上下文只保存在服务端审计元数据中，不发送主体哈希给浏览器。

| 事件类型 | 用途 | 关键字段 |
| --- | --- | --- |
| progress | 查询改写阶段进度 | stage、message、sequence、trace_id |
| query_rewrite | 原查询和改写查询 | original_query、rewritten_query、status、sequence、trace_id |
| answer_delta | 增量回答文本 | conversation_id、message_id、delta、sequence |
| citation | 可展示的引用来源 | citation_id、title、section、url、source_type |
| error | 可展示的异常或降级提示 | code、message、retryable |
| done | 本轮回答完成状态 | finish_reason、usage、trace_id |

所有事件均应包含会话关联标识、递增序号和 trace_id。对于无权限或隐私数据，citation 事件不得输出原始敏感字段或长期有效链接。

#### FR-OPS-001 查询日志与用户反馈

系统应异步记录用户角色、身份校验结果、原问题、改写问题、意图、路由、召回摘要、重排摘要、模型与 Prompt 版本、耗时、Token 用量、错误和 trace_id。日志中应对个人身份、车辆识别信息和敏感业务字段进行脱敏。

三类用户均可对完整助手回答提交“赞”或“踩”，并允许修改同一回答的评价。反馈应关联具体会话、消息、角色、引用和模型版本，为知识补充和回答优化提供依据；最近一次评价起保留一年。

#### FR-TASK-001 可靠异步任务

文档转换、Embedding、索引重建、异步审计与反馈聚合必须使用 Celery 5.4+、Redis 7+ 和 Relier 0.1 系列执行。Redis 必须启用 AOF 持久化并配置 `maxmemory-policy noeviction`；Relier 负责 Phoenix 恢复、原子 Redis Lua 幂等、两级超时、优雅关闭和 DLQ。

每个异步任务必须具有稳定业务幂等键、`trace_id` 和统一状态：`queued`、`running`、`succeeded`、`failed`、`cancelled`、`dead_lettered`。`dead_lettered` 必须保留最小必要任务元数据、失败原因、复活/重试历史和人工重放审计；Redis Lua 的原子性不得被误认为 MySQL、MinIO、Elasticsearch、Neo4j 或模型 API 的全局事务保证。

#### FR-API-001 写接口幂等与统一错误

所有创建、重试、取消、状态变更、反馈提交和可能触发费用或异步任务的写接口必须接收 `Idempotency-Key`。服务端须将调用方、接口、键、请求摘要、状态和原始响应关联保存；同一主体使用相同键和相同请求重放时返回首个结果，键复用但请求摘要不同返回可识别的冲突错误。

错误响应必须使用统一的 `code`、用户可展示的 `message` 和 `trace_id`，不得返回密钥、完整 ES/Cypher/SQL 查询、堆栈、内部路径或其他主体的资源存在性。

### 6.9 P0 核心 API 契约

P0 新增接口采用 `/api/v1` 前缀。已有原型接口在迁移前保持兼容；进入替换阶段前必须提供兼容期、调用方清单和回归测试，禁止静默改变已有客户端行为。

| 接口 | 作用 | 关键约束 |
| --- | --- | --- |
| `POST /api/v1/chat/conversations` | 创建会话与首条用户消息。 | 身份仅从服务端 Session 构造；必须带 `Idempotency-Key`。 |
| `POST /api/v1/chat/conversations/{conversation_id}/messages:stream` | 提交问题并建立 SSE 回答流。 | 不接受客户端角色、车辆或员工范围；建立流前完成身份与会话归属校验。 |
| `GET /api/v1/chat/conversations/{conversation_id}` | 查询会话快照。 | 按会话归属和最新权限过滤内容与引用。 |
| `POST /api/v1/documents` | 上传后台知识文档并创建处理任务。 | 仅经后台权限授权；服务端取得上传人，禁止使用客户端伪造的上传人字段。 |
| `GET /api/v1/tasks/{task_id}` | 查询异步任务状态与安全摘要。 | 仅返回调用方可见任务；不得泄露 DLQ 原始敏感载荷。 |
| `POST /api/v1/tasks/{task_id}:retry` | 请求重试可恢复任务。 | 必须带 `Idempotency-Key`；只有授权主体可重试且任务状态允许重试。 |
| `POST /api/messages/{message_id}/feedback` | 提交回答赞踩反馈。 | 必须带 `Idempotency-Key`；仅能评价当前主体自己的完整助手回答；同一回答可修改赞踩，保存最新评价、引用、模型和权限快照，最近一次评价起保留一年。 |
| `POST /internal/v1/agent/tools/{tool_name}` | Agent 调用受控业务工具。 | 仅内部服务身份可调用；业务后端重新校验身份上下文、参数、权限和 `trace_id`。 |
| `POST /internal/v1/hr/staff/{emp_id}/initial-password` | HR 为已创建员工设置一次性初始密码。 | 仅 `X-Internal-Service-Token` 可调用，必须携带 `Idempotency-Key`；仅限在职且空密码员工；不创建 HR 主数据，不返回密码或摘要，成功后撤销员工 Session。 |
| `PATCH /api/admin/staff/{emp_id}/access` | 管理员修改普通员工 `status`、`dept_id`。 | 仅在职且 `job=leader` 的员工可调用，目标必须为当前 `job=staff`；请求不得包含 `job`；必须带 `Idempotency-Key`；幂等记录保留 24 小时；更新成功后立即撤销目标员工全部 Redis Session，并保存六个月审计记录。 |
| `POST /api/documents/upload` | 在职员工上传待审核知识文档。 | 服务器以当前员工身份记录上传者；文档解析后处于 `PENDING_REVIEW`，不写入 ES。 |
| `GET /api/documents/review-queue` | 获取当前员工可见的审核列表。 | 不接受客户端上传人或权限范围；普通员工仅可见本人 `PENDING_REVIEW`、`REJECTED` 文档，`leader` 仅可见全部 `PENDING_REVIEW` 文档。 |
| `POST /api/documents/{document_id}/review` | 领导通过或驳回已解析文档。 | 仅 `leader` 可调用；通过时必须选择 `VISITOR`、`STAFF`、`LEADER` 并触发向量化，驳回不进入 ES。 |
| `POST /api/knowledge/search` | 按当前可信 Session 检索知识分片。 | 请求不得提交权限标签；后端从主体推导 `metadata.accessibleBy` 过滤范围。 |

SSE 使用 `progress`、`query_rewrite`、`answer_delta`、`citation`、`error`、`done` 六类事件。每个事件必须带会话关联标识、递增 `sequence` 和 `trace_id`；P0 每 15 秒发送 SSE 注释心跳，最大连接时长为 120 秒，`sequence` 同时作为 SSE `id`。客户端断开时立即取消上游模型流且不保存部分助手回答；P0 暂不支持 `Last-Event-ID` 续传或事件持久化。

### 6.10 P0 Web 前端

P0 Web 前端采用 **Next.js App Router、React 与 TypeScript**，仅面向浏览器提供页面展示、表单交互、SSE 事件消费与可鉴权引用展示；FastAPI `api_service` 继续是所有认证、授权和业务数据处理的可信边界。

| 需求 ID | 描述 | 验收标准 |
| --- | --- | --- |
| FR-WEB-001 | 提供公开入口、顾客/员工账号密码登录、会话列表、问答页、文档管理、任务状态和反馈页面。 | 页面仅调用 `/api/v1` 外部契约；无权用户不能通过路由参数或浏览器状态读取其他主体资源。 |
| FR-WEB-002 | 消费并展示 SSE 进度、查询改写、回答、引用、错误和完成事件。 | `progress` 显示“正在优化您的问题”，`query_rewrite` 返回原查询与改写查询，`answer_delta` 按序追加，`citation` 仅展示当前身份可访问的来源，断流显示可理解的失败或重试状态。 |
| FR-WEB-003 | 浏览器不保存或处理业务敏感凭据。 | 浏览器不持有数据库、模型、Neo4j、Redis 或 Agent 工具凭据；顾客和员工均使用 HttpOnly Cookie 关联的服务端 Session，密码校验只在服务端进行。 |

Next.js Route Handler 如用于同源转发、静态资源或页面会话辅助，不得复制 FastAPI 的领域规则、授权判断或数据访问逻辑；`apps/web` 不得直连 MySQL、Elasticsearch、MinIO、Neo4j、Redis、DashScope 或 Agent 内部工具。

### 6.11 P0 任务状态机与端到端闭环

~~~text
Web 用户提交问题
  → 服务端构造 AccessContext 并校验会话归属
  → qwen3.5-flash 意图识别与查询改写
  → 受控工具并行检索 ES / MySQL / Neo4j
  → 父子块补全、二次授权、qwen3-rerank 重排
  → qwen3.7-plus 生成引用和 SSE 事件
  → 异步记录查询、路由、证据、成本、反馈与 trace_id
~~~

可恢复异步任务的状态迁移只能为：`queued → running → succeeded`、`queued/running → failed`、`queued/running → cancelled`，或在达到复活上限后进入 `dead_lettered`。重试和 Phoenix 恢复必须创建可审计的尝试记录，且不能绕过业务幂等键与权限校验。

## 8. 非功能需求

### 8.1 安全与隐私

- 车主身份、车辆绑定、订单、维修与保养数据属于敏感业务数据，必须采用认证、最小权限、脱敏、审计和受控链接保护。
- P0 员工内部资料必须按在职状态和 `staff`、`leader` 员工类别过滤；不得仅依赖 Prompt 约束。`dept_id`、区域、车型或项目权限不属于 P0 员工授权条件。
- 密钥、Token 和数据库密码仅存放在受控密钥管理或运行环境变量中，不得写入代码、日志或版本库。
- 文件上传需具备类型、大小、恶意文件和重复文件校验。
- Agent 运行时必须使用独立身份和最小网络权限；不得挂载宿主机目录、Docker Socket、数据库配置或业务数据卷。
- 代码分析沙箱必须以非 root 用户运行，根文件系统默认只读，并限制 CPU、内存、并发数、执行时长和输出大小。

### 8.2 可维护性与扩展性

- Python 后端应按渠道适配、身份权限、文档、意图、改写、路由、数据源适配、重排、上下文、回答、审计和运营划分模块。
- 模型、Embedding、重排器、数据源和渠道使用可替换适配器，避免绑定单一供应商。
- Prompt、索引映射、数据模型、API 和 SSE 事件均需版本化并保证兼容策略。
- 生产环境的文档处理与异步日志不得长期依赖 Web 进程内任务，应采用 Celery + Redis + Relier 的可持久化、可重试任务机制。

### 8.3 稳定性与可观测性

- 每次请求、外部调用、异步任务和 SSE 会话都应携带 trace_id。
- 应监控文档处理成功率、检索耗时、首个回答事件时延、SSE 断连率、模型成功率、权限拒绝率和 Token 成本。
- MinerU、模型服务、ES、关系库、图数据库不可用时必须有超时、限流、熔断、重试和降级策略。
- 所有索引、日志和反馈写入应尽量幂等，避免重复回答、重复记录和重复计费。

## 9. 验收标准

| 编号 | 验收项 | 通过标准 |
| --- | --- | --- |
| AC-01 | 普通顾客权限 | 普通顾客可获得公开车型和服务答案，无法检索车主专属、内部或未公开资料。 |
| AC-02 | 已购车车主权限 | 已验证车主可查询本人授权车辆信息，无法访问其他车主记录。 |
| AC-03 | 员工权限 | 员工只能获得岗位授权的内部资料与数据，跨部门或敏感内容被正确拒绝或脱敏。 |
| AC-04 | 文档入库 | 支持的文件完成上传、MinerU 转换、切片和状态查询；仅领导审核通过的文档才向量化，失败可定位与重试。 |
| AC-05 | 检索上下文 | 子块命中后能回溯父块并补全同级兄弟块，补全结果不越权。 |
| AC-06 | 意图与路由 | 汽车领域问题进入相应数据源；闲聊和非领域问题不访问企业私有数据。 |
| AC-07 | 多源降级 | 一个数据源失败时，其他成功结果仍可使用；车主专属数据失败时不得猜测或伪造。 |
| AC-08 | 引用与回答 | 回答可定位来源；证据不足、冲突或权限不足时明确说明。 |
| AC-09 | 流式输出 | SSE 按 progress、query_rewrite、answer_delta、citation、error、done 六类事件输出并正常结束。 |
| AC-10 | 运营闭环 | 查询、权限、路由、检索、回答、错误和反馈可通过 trace_id 关联审计。 |
| AC-11 | 身份映射 | MySQL 员工账号的 `status` 与固定岗位值 `staff`、`leader`，以及服务端 Session 车主均可构造可信 AccessContext；员工状态或部门变更后，受影响 Redis Session 被立即清除；授权数据失效或 Neo4j 关系异常时不放宽权限。 |
| AC-12 | 任务可靠性 | Worker 被中断、任务超时、重复投递或毒丸任务时，任务可按状态机恢复、失败或进入 DLQ；相同业务幂等键不产生重复副作用。 |
| AC-13 | API 安全 | 私有资源跨主体访问返回不泄露存在性的错误；重复 `Idempotency-Key` 返回首个结果，摘要不一致时返回冲突错误。 |

## 10. P0 实施与联调指南

### 10.1 开发顺序

1. 完成第 11 节中所有 P0 上线阻断决策，并在评审记录中确定数据拥有者、接口调用方和验收人。
2. 先定义 Pydantic DTO、统一错误码、`Idempotency-Key` 行为、SSE 事件模型及 Agent 内部工具 HTTP/JSON 契约，再实现 Controller 或 Worker。
3. 在确认车主绑定后，以 Alembic 创建任务、查询、引用和反馈所需迁移；不得在应用启动时改 Schema。员工 P0 权限直接使用现有 `staff_info` 的 `status`、`job`、`dept_id`，不为区域或车型范围新增字段。
4. 实现普通顾客、车主、员工的 `AccessContext`、MySQL 员工账号与授权数据校验、按主体撤销 Redis Session 与资源归属校验，并先完成三类越权测试。
5. 接入文档审核、MinerU、切片、DashScope `text-embedding-v4`（1536 维）和 Elasticsearch 混合检索；完成父块回溯、兄弟补全与二次授权。
6. 接入受控 MySQL 只读查询和 Neo4j 查询 Adapter，限制可访问视图、标签、关系、返回量和超时；禁止模型直接生成可执行 SQL 或 Cypher。
7. 实现 `qwen3.5-flash` 意图/改写、`qwen3-rerank` 重排、`qwen3.7-plus` 回答、引用校验和 SSE，建立公开、车主、员工三类 RAG 评测集。
8. 接入 Celery、Redis、Relier，完成 AOF/noeviction 预检、Phoenix 恢复、DLQ、幂等、优雅关闭和预生产混沌测试。
9. 在 Web 完成会话、提问、SSE 展示、引用、任务状态和反馈闭环；钉钉等渠道不进入 P0。

### 10.2 P0 Definition of Done

- 所有 P0 接口、内部工具和 SSE 事件均有版本化契约、成功/失败/重复请求测试及安全错误文案。
- 三类角色均通过真实身份与权限数据验证；普通顾客不能读取车主或内部数据，车主不能读取他人数据，员工不能跨岗位范围读取内部数据。
- 每项回答均有可鉴权引用或明确的证据不足说明；不得伪造来源或个人车辆信息。
- 模型、ES、MySQL、Neo4j、MinerU、Redis 和对象存储均配置超时、限流、重试或降级策略，并产生可关联的 `trace_id`。
- 预生产环境验证 Redis AOF、`noeviction`、Relier Phoenix 恢复和 DLQ；完成 Worker 中断、网络异常、重复投递、慢任务与毒丸任务测试。
- P0 仅在 Web 渠道上线；监控、告警、备份、恢复演练、数据脱敏和删除流程满足已确认的生产要求。
